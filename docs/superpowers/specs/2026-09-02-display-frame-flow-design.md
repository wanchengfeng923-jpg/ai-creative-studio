# 展示类连续画面生成流程设计

## 1. 背景

当前展示类生成把一套方案和完整轮播结果混在一次文字请求中，且轮播提示词还包含旧的 `resolved_tags` 业务要求。本设计将展示类改为“首帧方案 + 按需后续画面”的流程，同时保留叙事类独立路径。

本设计只定义后端业务接口、状态和数据流。创意效果、写作风格、画面规则和转场规则由 GPT 侧配置，代码不复制这些业务规则。

## 2. 目标与非目标

### 2.1 目标

- 不轮播时，每套展示方案只生成一张图。
- 首次请求返回三套展示方案；每套方案先生成第 1 张图。
- 首次同时规划该方案的完整画面路线，但只实际生成首帧。
- 用户选择一套方案后，为该方案建立独立 GPT 会话。
- 用户点击继续时，一次规划并生成剩余画面；系统内部按画面顺序串行生成。
- 用户选择 AI 决定数量时，每套方案独立决定 2 至 5 张，并在方案内锁定。
- 后续画面只返回画面内容和承接信息，不重复返回方案说明和创意来源。
- 图片生成失败时自动重试一次，失败方案保留已成功画面并可从失败处继续。

### 2.2 非目标

- 本阶段不设计前端按钮、布局和展示细节。
- 不允许用户编辑或重新规划已经生成的画面路线。
- 不改变叙事类创意的业务规则。
- 不要求 GPT 输出 `resolved_tags`。
- 不把后续画面并行生成。

## 3. 三个提示词接口

### 3.1 叙事类创意

输入至少包含任务类型、任务描述、叙事类标签、产品信息和参考文件名。

输出为五个故事，每个故事包含两个钩子，每个钩子包含三个画面建议。后端只校验数量、字段、非空和 JSON 格式。

### 3.2 展示类首帧方案

输入：

```json
{
  "task_type": "...",
  "task_description": "...",
  "creative_tags": {},
  "carousel_mode": "none | fixed | ai",
  "requested_frame_count": 1,
  "aspect_ratio": "16:9",
  "product_info": "...",
  "reference_files": []
}
```

输出包含三套方案。每套方案包含方案说明、创意来源、锁定的 `frame_count`、视觉连续性规则、完整 `frame_plan` 和 `first_frame`。

规则：

- `carousel_mode=none` 时 `frame_count` 必须为 1，不能推荐后续数量。
- `carousel_mode=fixed` 时 `frame_count` 必须等于用户指定的 2 至 5。
- `carousel_mode=ai` 时每套方案独立返回 2 至 5。
- 首次只为每套方案实际生成 `first_frame`。

图片模型所需的 `image_generation_instruction` 是服务端字段，不进入公开响应和历史接口。

### 3.3 展示类后续画面

输入包含：方案完整信息、该方案 GPT 会话、完整画面路线、已完成画面、上一张实际图片、待生成画面序号、视觉连续性规则和画幅。

输出只包含待生成画面的：

```json
{
  "frames": [
    {
      "frame_index": 2,
      "content": "当前画面内容",
      "transition_from_previous": "从上一画面如何承接",
      "transition_to_next": "如何承接到下一画面",
      "ending_note": null,
      "image_generation_instruction": "服务端图片生成字段"
    }
  ]
}
```

后续响应不重复方案说明、创意来源和整体路线。最后一张使用 `ending_note` 表达收束，不要求下一张转场。

## 4. 业务流程

### 4.1 不轮播

```text
首帧提示词 -> 三套方案 -> 三张首图 -> 返回完整方案和首图 -> 完成
```

### 4.2 固定数量或 AI 决定数量

```text
首帧提示词
  -> 三套方案各生成第 1 张
  -> 用户选择一套
  -> 创建该方案独立 GPT 会话
  -> 后续提示词规划剩余画面
  -> 按序生成第 2 张、第 3 张……最后一张
```

用户一次点击生成剩余画面，但后端必须等待前一张完成后再提交下一张。三套方案之间没有连续性依赖，首图可以并行生成。

## 5. 会话和连续性

首次请求可以一次返回三套方案。用户选择后，为选中方案建立一个独立 GPT 会话，并注入：

- 方案完整信息
- 完整 `frame_plan`
- 第 1 张实际图片
- 第 1 张实际画面信息

同一方案后续请求始终使用同一 GPT 会话。每生成下一张，必须同时提供上一张实际图片、上一张画面信息、已完成画面记录和方案级视觉连续性规则。

目标是保持创意逻辑、关键视觉元素和转场关系连续，不承诺像素级一致。

## 6. 后端数据模型

### 6.1 方案级

```text
scheme_id
title
creative_summary
creative_sources
frame_count
visual_continuity_rules
frame_plan
conversation_id
```

### 6.2 画面级

```text
frame_index
planned_content
actual_content
transition_from_previous
transition_to_next
ending_note
image_status
image_path
attempt
```

`image_generation_instruction` 只保留在服务端内部对象或受保护的任务数据中，不进入浏览器历史响应。

## 7. 状态和失败处理

画面状态：

```text
pending -> generating -> success
                     -> retrying -> success
                                  -> failed
```

- 首图失败只影响对应方案，其他方案正常返回；该方案可单独重试。
- 后续画面失败自动重试一次。
- 重试仍失败则停止该方案后续画面，保留已成功画面，并允许从失败序号继续。
- 所有计划画面成功后，方案标记为 `completed`，不再接受继续生成。

## 8. 后端接口边界

- `app.py` 只处理 HTTP、权限、请求/响应包络和错误映射。
- `generation_service.py` 编排方案、会话、画面顺序和持久化。
- `prompting.py` 只负责将结构化输入交给 GPT 配置，不内置创意业务规则。
- `model_client.py` 只负责通用文字模型会话。
- `image_jobs.py` 只负责按顺序提交图片任务、重试和状态同步。
- `repository.py` 保存方案、画面、会话和任务状态，是事实源。

## 9. 验收标准

1. 不轮播每套方案只有一张图，且不出现数量推荐或继续生成状态。
2. 固定数量时所有画面数量等于用户选择值。
3. AI 决定时三套方案可分别返回不同的 2 至 5 张数量。
4. 首次显示三套方案各自的首图和完整画面路线。
5. 选中方案后只创建一个 GPT 会话，后续一直复用。
6. 后续画面按顺序生成，下一张使用上一张实际图片。
7. 后续返回不重复方案说明和创意来源。
8. 单张图片失败最多自动重试一次，失败后可从该画面继续。
9. `image_generation_instruction` 不出现在浏览器响应。
10. 叙事类路径和现有工作台 API 保持兼容。
