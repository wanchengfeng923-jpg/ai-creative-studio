# AI v2 文字优先与按需生图实施设计草案

- 日期：2026-09-04
- 状态：已批准用于制作独立纯前端预览
- 当前授权：只制作独立纯前端预览；不修改生产页面、不接 AI、不改数据库
- 批准说明：用户已确认精简结构，并要求旧 AI 冻结、新 AI 完全隔离，二者绝不可互相引用或叠加
- 适用范围：叙事类文字方案、展示类静态方案、展示类轮播方案、按需图片生成

> 本文是 AI v2 的精简业务契约。它取代重构总纲中针对新 AI 的“丰富字段建议”和旧视觉输出形状；总纲中的安全、治理、测试、回滚和旧实现冻结要求继续有效。

## 1. 背景与决定

现有页面、账号、项目和标签选择体验继续保留。现有 AI 生成链路停止扩展，作为历史实现冻结；新 AI 不在旧 builder、validator、结果字典、轮播编排和兼容字段上继续叠加逻辑。

新流程采用“文字优先、图片按需”的产品结构：用户先查看文字创意，只有认可某个展示类方案时才主动生成图片。叙事类不提供图片；展示类非轮播每套方案最多生成一张图片；展示类轮播按照已经规划好的顺序，每次点击只生成下一张图片。

本设计只固定 Prompt 在产品流程中的职责、三个输入字段和三类输出的业务含义，不决定最终 Prompt 正文、措辞、示例、创意方法和质量评测细节。这些内容将在前端预览确认后单独设计和审批。

## 2. 目标

1. 保留现有页面视觉和展示类标签逻辑，不重写已经稳定的非 AI 功能。
2. 将旧 AI 与新 AI 完全隔离，避免新增兼容分支。
3. 让文字生成先于图片生成，图片默认不生成。
4. 让用户看见的创意结果保持精简，内部图片执行信息不进入浏览器。
5. 固定一个小型输入 Interface，使标签目录变化不要求修改后端业务代码。
6. 使用版本化 JSON Schema 校验输出，减少手写字段转换。
7. 先用纯前端假数据验证产品流程，再制定生产改造计划。

## 3. 非目标

本轮不包含：

- 修改或优化现有 Prompt；
- 调用真实文字模型或图片模型；
- 修改现有生产页面；
- 修改 SQLite 表或迁移真实数据；
- 删除旧 AI 文件、Prompt、测试或历史数据；
- 视频生成、视频入口或视频状态；
- 参考资料理解、证据台账、素材计划、制作风险或评审说明；
- 重新设计现有标签目录和展示类轮播选择逻辑。

## 4. 冻结与隔离原则

### 4.1 旧 AI 冻结

旧 AI 代码只允许用于读取历史事实、对照行为和迁移验证。新功能不得新增对以下旧实现的调用：

- 旧 Prompt builder；
- 旧手写 validator；
- 旧视觉兼容字段 mapper；
- 旧轮播文字续写流程；
- 旧自动生图流程；
- 旧生成结果字典。

冻结不等于立即删除。旧代码和旧数据在新流程验证完成前保留，以便回退和核对。

### 4.2 新 AI 独立

新 AI 使用独立 Module、独立路由、独立 Prompt/Schema registry 和独立测试入口。新实现可以复用底层文字模型与图片模型 Adapter，但不得继承旧业务契约。

以下要求是不可通过兼容需求、迁移便利或临时降级绕过的硬不变量：

- **零引用**：新 AI 不得导入、调用、继承或间接委托给旧 AI 的 builder、validator、mapper、结果字典、轮播编排、业务 schema 或生产入口；
- **零回退**：新 AI 失败时只能按新链路定义的失败状态处理，不得回退到旧 Prompt、旧模型调用或旧图片流程；
- **零双写、零双读**：一次新 AI 请求只能写入和读取新链路自己的业务事实，不得同时写入旧新结构，也不得合并读取旧新结果后对外呈现；
- **零兼容串联**：不得以 compatibility adapter、mapper、feature flag 或 fallback router 将新旧 AI 串成一条调用链；
- **中立基础设施例外**：只允许复用不包含创意业务语义的基础设施，例如 HTTP 客户端、供应商传输 Adapter、日志和通用任务队列。若现有基础设施位于旧 AI 命名空间，必须先抽取到第三方公共位置，再由新旧两侧分别依赖；新 AI 不能反向依赖旧 AI；
- **单向切换**：正式切换只能发生在上层入口的路由选择处，一次请求从入口开始就明确进入旧链路或新链路，进入后不得跨越边界。

### 4.3 预览与生产隔离

第一版预览是独立静态页面，使用内置假数据和模拟状态。它不得请求生产 API，不得写入数据库，不得修改正式 `static/index.html` 或 `static/app.js`。

预览自身也必须证明隔离边界：页面全部数据和状态机内联，不加载生产 JavaScript、生产 CSS、旧 AI 资源、远程资源或任何接口。浏览器网络面板中打开本地文件后的业务请求数必须为零。

## 5. 产品流程

### 5.1 公共输入流程

用户继续在现有页面中选择脚本类型、填写任务说明、选择画面比例和创意标签。展示类的非轮播/轮播判断及屏数选择沿用现有逻辑，不新增第三个顶层脚本类型。

提交给新 AI 的业务输入固定为三个字段：

```json
{
  "task_description": "任务说明",
  "aspect_ratio": "16:9",
  "creative_tags": {
    "目标人群": ["经典武侠用户"],
    "产品卖点": ["装备成长"]
  }
}
```

用例类型由调用入口和现有页面状态决定，不作为第四个模型输入字段。展示类轮播开关、屏数和形式继续作为用户已选标签包含在 `creative_tags` 中；输入标准化只删除空值，不删除这些已选控制项。因此轮播 Prompt 可以从同一个 `creative_tags` 对象读取用户实际选择的屏数和形式。

新 AI v2 不读取“产品证据/补充资料/参考文件”字段。它们不属于这三个输入字段；现有旧页面和旧数据在冻结链路中保留，未来如需支持资料输入，必须另行设计输入契约和迁移任务，不能偷偷把资料塞进 v2 Prompt。

`creative_tags` 是开放的“标签组到已选值数组”映射。统一输入标准化 Module 执行以下规则：

- 未选择的标签组不进入对象；
- 空字符串和空数组不进入对象；
- 重复值只保留一次；
- 没有任何已选标签时发送空对象 `{}`；
- 后端不维护标签组名称白名单；
- 已选择标签是硬约束，未选择标签表示 AI 可以自由发挥；
- AI 补充的方向不得冒充用户已经选择的标签。

### 5.2 叙事类

每批返回 5 套文字方案。每套包含：

- 一句话故事；
- 2 个钩子；
- 每个钩子 3 个画面描述，共 6 个画面描述。

叙事类不展示图片按钮，也不产生内部生图 Prompt。

输出契约轮廓如下；精确 JSON Schema 在预览确认后编写：

```json
{
  "schema_version": "narrative-text-v1",
  "items": [
    {
      "story": "一句话故事",
      "hooks": [
        {
          "text": "钩子一",
          "scenes": ["画面一", "画面二", "画面三"]
        },
        {
          "text": "钩子二",
          "scenes": ["画面四", "画面五", "画面六"]
        }
      ]
    }
  ]
}
```

### 5.3 展示类非轮播

每批返回 3 套文字方案。每套公开显示：

- 方案标题；
- 核心创意；
- 广告文案；
- 画面描述；
- “生成图片”按钮。

文字 AI 同时返回一条仅供服务端使用的生图 Prompt。该 Prompt 不进入公开响应。

输出契约轮廓如下；精确 JSON Schema 在预览确认后编写：

```json
{
  "schema_version": "static-text-v1",
  "items": [
    {
      "title": "方案标题",
      "core_idea": "核心创意",
      "ad_copy": "广告文案",
      "image_description": "用户可见的画面描述",
      "execution": {
        "image_prompt": "服务端使用的完整生图提示词"
      }
    }
  ]
}
```

`image_description` 表达创意事实，`execution.image_prompt` 只负责把同一事实翻译为图片模型可以执行的指令。生图 Prompt 可以补充构图、镜头、光照、材质、质量和负面限制等表现手段，但不得增加画面描述中不存在的新人物、新产品事实或新剧情。

### 5.4 展示类轮播

展示类入口、轮播标签、屏数和形式选择保持现有逻辑。每批返回 3 套文字方案。每套公开显示：

- 方案标题；
- 核心创意；
- 广告文案；
- 按顺序排列的每张画面描述；
- 当前允许执行的单个图片按钮。

文字 AI 在首次生成时一次性规划全部画面，并返回内部视觉一致性规则及每张图片对应的生图 Prompt。后续图片生成不再次调用文字 AI。

输出契约轮廓如下；精确 JSON Schema 在预览确认后编写：

```json
{
  "schema_version": "carousel-text-v1",
  "items": [
    {
      "title": "方案标题",
      "core_idea": "核心创意",
      "ad_copy": "广告文案",
      "frames": [
        {"index": 1, "description": "首张画面描述"},
        {"index": 2, "description": "第二张画面描述"},
        {"index": 3, "description": "第三张画面描述"}
      ],
      "execution": {
        "continuity_rules": ["主体身份一致", "服装和产品特征一致", "美术风格一致"],
        "image_prompts": [
          {"index": 1, "prompt": "第1张完整生图提示词"},
          {"index": 2, "prompt": "基于上一张图片生成第2张的完整提示词"},
          {"index": 3, "prompt": "基于上一张图片生成第3张的完整提示词"}
        ]
      }
    }
  ]
}
```

公开 `frames` 与内部 `image_prompts` 必须按 `index` 一一对应。内部 Prompt 可以补充图片模型执行所需的表现手段，但只能实现对应公开画面描述，不得建立第二套剧情或增加新的产品事实。

三个结果的 `schema_version`、`items`、公开业务字段及轮播 `frames[].index` 均属于浏览器可见传输契约。`execution` 及其全部后代字段属于服务端内部契约。按钮和图片状态是网页及运行状态，不是文字模型输出字段。

输出契约必须满足以下不变量：

- 叙事 `items` 恰好 5 项，每项恰好 2 个钩子，每个钩子恰好 3 个场景；
- 静态 `items` 恰好 3 项，每项有且只有一条内部生图 Prompt；
- 轮播 `items` 恰好 3 项；每套帧数符合已选轮播屏数，帧索引从 1 连续递增；
- 轮播公开帧和内部生图 Prompt 的数量、索引完全一致；
- 未声明的输出字段默认拒绝，不允许模型通过额外字段绕过公开/内部契约。

### 5.5 批次与文字会话

- 同一定位最多生成两批；第二批仍返回该用例固定数量的方案。
- 每一批都直接创建新的文字模型会话，不复用第一批的 `conversation_id` 或 `parent_message_id`，也不读取旧 AI 会话。
- v2 不要求第二批显式声明“必须与第一批不同”，不把第一批摘要注入第二批 Prompt；`batch_index` 只作为运行记录和额度限制元数据，不是第四个业务输入字段。
- 第二批失败只影响第二批运行，不回写或覆盖第一批结果。
- 文字模型输出结构错误不做隐藏的格式修复调用；该批直接进入失败状态。用户主动重试时才创建新的文字会话。

每次文字生成请求只创建一个文字会话并等待该会话返回整批文字结果；前端不会为每个方案或每个字段额外打开文字会话。

## 6. 图片执行规则

### 6.1 状态

每张图片只有四个状态：

```text
pending     尚未生成，可以点击生成
generating  正在生成，按钮禁用
success     生成成功，在当前方案版本内永久锁定
failed      生成失败，可以重试当前张
```

成功图片在当前方案版本内不可重新生成。锁定键由稳定的方案版本和帧索引组成；相同锁定键的重复点击或重复请求必须返回已有状态，不得创建第二个成功版本。失败不构成正式图片，因此允许以相同锁定键重试。

### 6.2 静态图片

静态方案只允许生成一张图片：

```text
用户点击生成图片
-> 服务端读取该方案的 execution.image_prompt
-> 调用图片模型
-> 成功后锁定，按钮变为已生成
```

### 6.3 轮播图片

轮播严格串行：

```text
第1张 = 查找 index=1 的 image_prompts.prompt
第2张 = 第1张实际图片 + 查找 index=2 的 image_prompts.prompt
第3张 = 第2张实际图片 + 查找 index=3 的 image_prompts.prompt
第N张 = 第N-1张实际图片 + 查找 index=N 的 image_prompts.prompt
```

只有上一张成功后，下一张的生成按钮才可用。一次“生成图片”点击最多推进当前方案的当前一张，不预取、不自动推进、不在后台偷偷生成后续帧。成功图片不可重新生成，因此不存在前序图片变化导致后续图片作废的分支。

### 6.4 会话边界

- 文字生成会话与图片生成会话是两类不同资源。文字模型不负责后续图片续写。
- 一批文字结果只创建一个文字会话。用户选择某个展示方案生成图片时，为该方案创建一个独立图片会话；因此 3 个方案都生成图片时，总计是 1 个文字会话和 3 个图片会话。
- 静态方案的全部图片工作只发生在该方案自己的图片会话中，并且最多成功一张。
- 轮播方案的全部帧共享该方案自己的图片会话；第 N 张必须携带第 N-1 张已成功的实际图片和第 N 张内部 Prompt，不再次调用文字模型。
- 图片会话的 `conversation_id`、`parent_message_id` 或供应商等价游标只在 v2 图片 Adapter 和图片尝试记录中保存，属于私有 typed `ImageSessionCursor`，不能进入公开 DTO，也不能跨到旧 AI。
- 图片会话键由文字运行、方案版本和方案用途稳定生成；同一方案第一次点击才允许创建图片会话。该方案后续帧、重复点击和失败重试都必须复用这一个图片会话。
- 图片请求幂等键由方案版本和帧索引稳定生成；失败重试使用同一逻辑帧键，并以递增 attempt 序号区分尝试，不改变图片会话。
- 网页超时、连接断开或 5xx 只说明本地没有拿到确定结果，不等价于供应商失败。重试前必须先查本地 attempt，再用原图片会话的供应商游标/job 引用执行对账。
- 图片 Adapter 提交供应商请求时必须携带稳定的 `image_session_key` 和 `request_key`；这样即使本地 cursor/attempt 写入失败，也能按稳定键向供应商查询原任务。供应商不支持按稳定键查询时，只能判定为未知并停止新提交，不能用盲目重发代替对账。
- 对账结果为“已成功”时下载并原子完成原 attempt；结果为“仍在工作”时重新挂接并继续轮询；只有供应商明确返回终态失败时，才在原图片会话内创建同一帧的新 attempt；结果未知、供应商不可用或查询超时时不创建新 attempt，保留可重试状态并等待下一次对账。
- 如果网页曾经拿到成功结果但本地 attempt 写入失败，重试可能只找到已存在的方案图片会话而找不到本地 attempt；此时按方案会话和稳定 request key 做孤儿任务对账，成功/工作中则恢复或重建本地 attempt，仍不创建第二个图片会话。
- 若网页显示失败但供应商会话实际已经成功或仍在工作，重试必须先完成上述会话对账并复用原会话产出；不能直接创建第二个图片会话。

会话数量以“实际点击过的方案”为准：

| 用户动作 | 文字会话数 | 图片会话数 | 说明 |
|---|---:|---:|---|
| 只生成一批文字 | 1 | 0 | 叙事类到此结束；展示类图片仍为 pending |
| 点击一个静态方案 | 1 | 1 | 该方案最多成功一张 |
| 点击一个轮播方案的多张帧 | 1 | 1 | 所有帧在同一图片会话中串行生成 |
| 三个展示方案都点击生图 | 1 | 3 | 总计 4 个供应商会话 |

失败重试、重复点击和网页重新加载都不增加上表中的图片会话数。

这里的“会话”指供应商侧的 conversation/session 资源，不是网页弹窗或用户需要管理的多个聊天窗口；会话 ID 对浏览器隐藏，网页只呈现文字结果、图片状态和可执行按钮。

## 7. Prompt 作用流程

新流程中，Prompt 的作用位置固定如下：

```text
网页标准化三个输入字段
-> 根据叙事/静态/轮播选择一个文字 Prompt
-> 将输入作为数据区一次性注入
-> 文字模型返回对应版本的 JSON
-> JSON Schema 校验结构
-> 内部结果按原样保存
-> 公开投影从空对象开始，只复制该 schema_version 明确允许的公开字段
-> 网页只渲染公开字段
-> 用户点击图片按钮
-> 图片 Module 读取对应内部 Prompt 和参考图片
-> 调用图片模型
```

以下流程职责已经固定，不属于后续 Prompt 文案讨论范围：

- Prompt 决定模型生成什么内容；
- JSON Schema 判断返回形状是否合法；
- 公开投影决定浏览器可以看到什么；
- 网页决定如何呈现公开字段；
- 后端图片编排只识别 `execution` 中稳定的执行字段。
- v2 不在文字链路中隐藏格式修复调用；输出结构错误直接失败，用户重试才会建立新的文字会话。

## 8. Prompt 专项设计阶段

纯前端预览确认后，Prompt 进入独立设计阶段。该阶段不改变本文已经固定的三个输入字段、三类业务输出含义和图片执行顺序，也不复用旧 Prompt 正文。该阶段必须依次完成：

1. 将本文确定的三种业务输出转化为各自唯一、清晰的模型任务；
2. 确定三个既定输入字段在 Prompt 数据区中的具体序列化格式；
3. 细化既定公开字段和内部执行字段的内容质量约束；
4. 编写少量高质量正例和失败例；
5. 用固定真实任务比较候选 Prompt；
6. 检查创意差异、任务理解、画面可执行性和公开/内部一致性；
7. 用户审批 Prompt 后才允许接入新后端。

最终 Prompt 文本不属于本草案的评审范围。本文固定 Prompt 在系统中的位置、三个输入字段、三类业务输出含义和职责；后续只设计实现这些约束的具体文案、示例、创意方法和评测方式。

## 9. 纯前端预览范围

文档确认后，下一步只创建独立预览页面。预览要求：

1. 延续现有页面的视觉语言，不重新设计标签选择页。
2. 使用固定假数据展示叙事 5 套、静态 3 套和轮播 3 套结果。
3. 静态方案初始只显示文字和“生成图片”按钮。
4. 轮播初始显示完整文字路线，但不显示任何已生成图片。
5. 点击按钮只模拟 `pending/generating/success/failed` 状态，不发送网络请求；预览使用的按钮不是模型输出字段。
6. 轮播每次只解锁下一张；成功后不可再次点击；失败状态可以重试。
7. 桌面和移动视口均无横向溢出、文字重叠或按钮跳动。
8. 预览不得导入旧 AI 模块，也不得修改生产数据库和配置。

建议预览放在独立目录：

```text
.scratch/ai-v2-text-first-preview/
```

## 10. 后续实施阶段

纯前端预览已获得确认，正式实施计划见 [`docs/superpowers/plans/2026-09-04-ai-v2-text-first-implementation.md`](../plans/2026-09-04-ai-v2-text-first-implementation.md)。正式实施仍按以下顺序推进：

1. 建立当前工作树的可回退冻结点；
2. 建立新输入标准化 Module 和版本化 JSON Schema；
3. 完成三种文字 Prompt 的专项设计与真实案例评测；
4. 实现独立文字生成链路；
5. 实现静态按需生图；
6. 实现轮播逐张生图和失败重试；
7. 将正式页面入口切换到新链路；
8. 观察稳定后删除旧 AI 生产入口；
9. 最后决定旧代码和旧数据的归档或迁移策略。

任何阶段都不得通过修改旧 AI 兼容分支来实现新需求。

## 11. 预览验收标准

纯前端预览通过需要同时满足：

- 三种结果形态与本文一致；
- 展示类非轮播/轮播判断仍符合现有标签逻辑；
- 默认不显示自动生成图片；
- 静态图片只能成功生成一次，失败可重试；
- 轮播只能按顺序逐张生成，成功图片不可重生成；
- 一次点击只推进一张；失败重试先模拟本地 attempt 与供应商会话对账，不能因为网页失败而增加图片会话；
- 用户能够在不阅读说明文字的情况下理解按钮当前会做什么；
- 预览运行时不产生任何真实 AI、图片、数据库或生产项目写入；
- 正式页面和旧 AI 运行行为保持不变。

## 12. 风险控制与回退

- 预览阶段仅新增独立静态文件，删除预览目录即可完整回退。
- 新 AI 实施前先建立可复现冻结点，避免当前未提交工作树成为模糊基线。
- 公开结果从空对象按当前 `schema_version` 的白名单重建，`execution` 整体禁止进入浏览器。
- 图片任务按方案和帧建立稳定标识，重复点击不得创建第二个成功版本。
- Prompt、Schema 和运行版本必须一一对应，禁止原地覆盖已产生历史结果的版本。
- 新链路未通过真实案例评测前，不替换旧生产入口。

## 13. 评审结论

用户已确认：

1. 采用本文定义的三类公开文字结构；
2. 静态和轮播的内部生图 Prompt 由首次文字 AI 一次性返回；
3. 轮播逐张生成，成功锁定且失败可重试；
4. 先制作独立纯前端预览，再讨论 Prompt 正文和正式改造计划；
5. 旧 AI 冻结，新 AI 与旧 AI 绝不可互相引用、回退、双写/双读或通过兼容层叠加。
6. 正式迁移使用独立 v2 路由和页面；文字同步返回，图片按需异步生成；同一定位最多两批，每批使用新的文字会话，不要求第二批显式去重。
7. v2 只接收任务说明、画面比例和创意标签；产品证据、补充资料和参考文件暂不进入 v2。
8. 会话按批次文字与方案图片分配：三个展示方案都生图时为 1 个文字会话 + 3 个图片会话；轮播每个方案的所有帧共享其图片会话，重试不新建第二个图片会话。

本次批准只授权制作独立纯前端预览，不代表批准修改生产代码或接入真实 AI。
