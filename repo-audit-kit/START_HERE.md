# 仓库整理：多会话执行说明

版本：1.0 · 编制日期：2026-09-08
适用任务：仓库盘点、文档核对、规则整理与进度记录治理。
状态：任务包已准备；尚未访问你的项目，未执行任何仓库审计。

## 为什么建议拆成多个会话

这类任务可能超过单个会话适合处理的工作量，尤其是模块多、历史长、文档互相矛盾时。除了仓库材料，检索输出、检查日志、修改与复核也占用上下文。模型允许输入的最大长度，并不是任务质量的保证。

目前不能在未查看仓库、模型和实际工具的情况下，准确估计需要多少会话，也没有适用于所有模型的固定“最佳上下文占用百分比”。这里采用工程上的任务边界：每次只完成一个范围清楚、可以检查并交接的工作单元。

Anthropic 的工程资料支持按需检索、结构化记录与增量交接，同时也指出摘要不能独自解决长任务问题。下面的具体任务卡是为本次需求设计的执行方案，不是论文证明的唯一最佳流程。

- [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

## 你如何使用

1. 将压缩包解压到要整理的仓库中，确认有 `repo-audit-kit/RUN_ONE_TASK.md`。不要覆盖仓库里原有的同名目录；遇到重名时另选目录，并在启动语句中使用真实路径。
2. 在能访问该仓库的编码 AI 中开一个新会话，发送下方启动语句。
3. 等它完成本轮、写好交接并明确结束，再开新会话。后续使用同一句启动语句即可。
4. 各会话必须访问同一个持续保存的工作区。更换环境时，要同步代码、未提交修改、任务包以及审计记录目录；仅开新聊天不会自动传递这些文件。
5. 如果 AI 报告需要业务判断或缺少必要访问，处理报告中的具体问题，再使用同一句话继续。遇到“完成”状态时不用继续开会话。

**每次都可以发送的启动语句：**

> 请读取仓库中的 `repo-audit-kit/RUN_ONE_TASK.md`，按它执行本轮任务。首次初始化；后续根据持久化状态继续。每次只完成一个有明确范围的子任务，完成或达到可安全交接的边界后保存记录并结束，不要在同一会话继续下一个子任务。

这次用户选择了逐会话推进，因此“本轮结束”是有意的任务边界。不要把它理解成需要每完成一步都询问许可。

## 8 个阶段，按需要重复

| 阶段 | 本轮只做什么 | 何时重复 |
| --- | --- | --- |
| T01 | 建立基线、范围、全局清单和任务队列 | 大型仓库清点尚未覆盖时继续拆分 |
| T02 | 盘点一个模块或一条业务路径 | 直到所有纳入范围的模块均完成约定深度 |
| T03 | 核对一组相关文档与对应实现 | 直到有效文档、规则声明和历史状态均已核对或明确标记缺口 |
| T04 | 核对一组跨模块关系，确定整理去向 | 直到跨模块问题、规则冲突和迁移关系已处理或登记阻塞 |
| T05 | 整理一组相互关联的规则 | 按规则作用域分批，确保含义和加载行为正确 |
| T06 | 修订一组文档，或迁移一批进度记录 | 按主题、任务或时间段分批，直至全部目标完成 |
| T07 | 验证一批改动并处理对应发现 | 检查失败时追加有边界的修复与复核任务 |
| T08 | 在新会话中完成独立验收 | 失败后修复，再用新的会话重新验收 |

这是 8 种任务卡，不是“保证 8 个会话结束”。通常每张卡至少执行一轮；不适用的工作须有理由。第一次盘点后，AI 会根据真实模块和文档规模生成具体队列。你不用预先猜会话数。

默认顺序为 T01、各批 T02、各批 T03、各批 T04、各批 T05、各批 T06、各批 T07、T08。任务队列记录实际依赖；相互独立的工作可在不跳过前提的情况下推进，阻塞项不会自动消失。

## 新会话只需要哪些信息

每轮入口是 `RUN_ONE_TASK.md`。它让 AI 先读取短状态文件，再按队列挑一条可执行任务，随后只读对应任务卡、必要证据和适用规则。

完整研究指南位于 `reference/AI仓库盘点与文档规则整理执行指南.md`，仅在需要方法、模板或原始来源时读取对应章节。原指南第 1 节描述整体目标；本任务包明确要求每次只执行一个子任务，不应据此在同一会话做完全部阶段。

不要把整套任务包、全部历史报告或完整研究指南配置成每次自动加载的规则，也不需要把整段旧聊天粘贴到新会话。

## 进度保存在哪里

默认记录目录是 `docs/repo-audit/`。若已有合适位置，T01 可以复用，并在任务包的 `ACTIVE_RUN.md` 记录真实路径。重要状态必须保存成可访问文件，不能只留在聊天中。

| 记录 | 用途 |
| --- | --- |
| STATE.md | 当前目标、位置、阻塞、下一步；持续替换现状 |
| QUEUE.csv | 每个具体任务的范围、依赖、状态和报告入口 |
| coverage.csv | 文件清点与实际审查深度 |
| findings.csv | 发现、证据、处理状态和验证入口 |
| reports/ | 每个任务的证据与结果，按需读取 |
| acceptance-questions.md | 预先确定的新会话验收问题，不含答案 |

这些是同一次审计的轻量记录。小仓库可以减少辅助文件，但需要保留唯一状态入口和明确的任务队列。不要另外维护一份内容相同的总进度流水账。

## 什么时候应当结束本轮

完成一个子任务并验证后就结束。若还没完成，但继续会涉及新的大模块、加载大量无关材料、反复丢失已确认的约束，或者工具已经提示上下文不足，应先保存中间结果，再将剩余范围拆成下一任务。

不要等到完全耗尽上下文才写交接；也不要仅因达到某个文件数就强行拆开必须一起保持一致的修改。如果本轮发生自动压缩，先核对记录和工作区，再决定是否还能完成当前单元。

本方案不规定神奇的 token 百分比、固定时长或统一文件数。任务规模根据实际复杂度调整，任何数字预算只可作为项目自己的提醒。

## 完成的判断

只有在约定范围内的任务、覆盖记录、问题处置和必要验证互相一致，且 T08 已独立核实后，才可标记全部完成。仍存在不可验证范围时要写清限制；阻塞关键工作的缺口尚未解决时，不能宣布完成。

交接资料不能代替原始证据。新会话应对当前任务的重要结论回到实际文件和检查结果核实，避免把上一轮推断越传越像事实。
