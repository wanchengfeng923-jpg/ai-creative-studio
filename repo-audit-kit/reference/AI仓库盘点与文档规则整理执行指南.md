# AI 仓库盘点与文档规则整理执行指南

版本：1.0
资料核验日期：2026-09-08
用途：交给能够读取仓库、检索文件和运行本地检查的编码 AI，执行仓库盘点、文档核对、规则整理与进度记录治理。
文档性质：研究汇总与执行规范。尚未检查具体仓库，文中的问题示例和记录模板均不是对你的仓库作出的事实判断。

**使用方式：把本文件提供给编码 AI，并要求它“按照第 1 节执行本次仓库整理任务，参考后续章节完成验证”。若它能够自行获取仓库信息，无须先让你填写全部背景。**

本文件是本次整理任务的工作说明。不要把全文复制进仓库的 AGENTS.md、CLAUDE.md 或其他每次自动加载的规则文件。整理完成后，只把仍需长期适用的少量规则保留在对应入口。

## 1. 可直接交给 AI 的执行指令

以下内容是一份完整任务说明。实际执行权限以用户当次指令、已有授权和运行环境的有效约束为准；本说明不会自动授予额外访问、发布或修改权限。

### 1.1 任务目标

请对当前仓库进行系统盘点、文档与实现核对、项目规则整理，以及过长进度记录治理。最终交付应使下一次新会话能够迅速确认项目当前状态、找到可信资料、识别应遵守的规则，并继续工作。

请完成实际检查和已获授权的整理工作，不能只给建议、目录树或一份泛泛的架构总结。每项重要结论必须有可追溯依据；无法判断的内容明确保留为未知或待确认。

本次默认关注仓库知识和工作规则。业务代码重构、依赖升级、部署方式变更等发现，先记录为独立后续事项；只有用户已明确把它们纳入任务时才执行。

### 1.2 执行原则

1. 先识别仓库根目录、当前版本、未提交工作、实际使用的 AI 工具与有效规则来源。遵守现有有效约束，不能通过改写规则为自己的行动解除限制。
2. 先形成基线和盘点记录，再修改目标文档。盘点阶段允许创建报告和检查记录；不要同时改动业务实现。
3. 对纳入范围的每个自有模块、规则文件和项目文档建立审查状态。将“已列入清单”“已阅读内容”“已交叉核对”“已运行验证”分开记录。
4. 将结论区分为已证实事实、基于证据的推断、待确认意图。代码说明实际实现；需求和决策说明预期行为；测试说明已检查的部分。三者冲突时不能直接把代码当成业务正确性的最终依据。
5. 规则整理以真实项目约束为依据。保留适用范围、理由、例外与验证方法；合并重复内容、修复失效路径，不能为了压缩文字而删去仍有效的要求。
6. 将稳定规则、架构解释、当前状态、任务计划与历史记录分别安排用途。优先复用现有文件，避免同时维护两份相同事实。
7. 整理长进度文件前，先提取未完成事项、阻塞、仍有效的决策和失败尝试的原因；核对状态后再迁移归档，保留追溯关系。
8. 按实际工具的加载机制安排规则；普通链接、自动导入、路径匹配并不等价。检查新会话实际加载了哪些规则，不以“文件存在”代替生效验证。
9. 分批完成已获授权、证据充分的整理，及时检查链接、命令和语义是否保持一致。无法判断的业务问题汇总后询问，并继续处理其他不依赖该答案的事项。
10. 保留用户未提交的改动；不要为获得干净状态而重置、删除或覆盖。不要为通过检查而跳过测试、弱化断言或扩大忽略范围。
11. 不要仅凭没有搜索到引用，就删除源文件、脚本、配置、迁移、测试或文档。对疑似无用项记录入口、动态引用、外部依赖及判断缺口。
12. 不要将本指南或每次任务流水账追加为永久规则。任务结束时更新确实变化的知识；没有变化的规则可以保持不动。

### 1.3 工作顺序

1. 建立基线与范围：版本、工作区状态、环境、有效规则、已有检查及无法访问的材料。
2. 完成仓库清点：模块、入口、构建与运行路径、测试、配置、部署、文档、任务记录和归档。
3. 按模块交叉核对：追踪关键调用链，核对文档声明、命令、路径、接口和完成状态。
4. 形成问题台账与整理映射：记录证据、影响、置信状态、拟处理方式和验证办法。
5. 执行文档与规则整理：先修复明确错误，再合并重复、提取当前状态、归档历史、建立有效入口。
6. 验证与交接：检查差异、路径、规则加载和任务连续性，交付实际完成项、未解决项及下一步。

### 1.4 必须交付的结果

- 一份审计报告：范围、基线、模块地图、主要问题、已完成整理及仍存在的限制。
- 一份覆盖记录：每个纳入范围的文件或可解释的文件集合，对应实际审查深度与排除理由。
- 一份发现与处理记录：重要问题的证据、判断、处理结果，以及未解决事项。
- 整理后的实际规则和文档，以及旧内容到新位置的迁移说明。
- 一份验证与交接记录：执行过的检查、结果、新会话验证、下一步及仍需用户判断的具体问题。

这些可以是同一报告中的章节；文件很多时再把清单拆成 CSV。不要为了满足文件数量而生成重复报告。若只有只读权限，交付可审查的补丁或逐项修改稿，并明确尚未应用。

### 1.5 完成条件

完成意味着约定范围已被盘点，重点内容已交叉核对，已授权且证据充分的整理已落实，关键规则仍有效，未完成事项没有在压缩中丢失，验证结果可以复核。

不允许把“没有找到问题”“测试通过”或“已经读取很多文件”扩展成“仓库绝对没有问题”。无法访问、未核对和未运行的部分应继续列出。

## 2. 研究结论与方法选择

### 2.1 可以让 AI 做到什么

AI 适合承担文件清点、跨文件检索、命令与路径核对、文档初稿整理、重复规则识别、进度提取和检查执行。其结果能否可靠，取决于来源完整性、任务边界、验证能力和问题反馈。

对于历史上未记录的业务理由、外部系统约束或产品承诺，AI 无法仅从当前代码恢复确定答案。对于全仓架构重构，自动整理文档也不能替代行为验证与工程判断。

### 2.2 研究并未给出一种普遍最优的规则文件方案

| 证据 | 主要发现 | 适用边界 |
| --- | --- | --- |
| ETH Zurich 等，Evaluating AGENTS.md，2026-06 修订版 [S01] | 在所测任务中，上下文文件通常未提高任务成功率，平均推理成本增加超过 20% | 基于 Python 仓库和特定模型、任务；不能推断所有项目都不需要规则 |
| Vercel，Next.js 文档实验，2026-01 [S02] | 无文档基线为 53%，明确要求使用 Skill 为 79%，8KB 文档索引方案达到 100% | 特定 Next.js 任务的内部评测；不能推广成 AGENTS.md 全面优于 Skills |
| Lulla 等，2026-01 论文及 ICSE JAWs 展示 [S03] | 10 个仓库、124 个 PR 中，中位耗时下降约 28.6%，输出 token 下降约 16.6% | 指标侧重效率；与任务成功率研究并非同一个实验 |

这些结果不支持“文件越长越好”“越短必然越好”或“换一种文件名就能提升质量”。S01 的修订版也没有发现文件长度能够单独解释其主要结果。需要在自己的任务上评测改动效果。

### 2.3 工程实践支持哪些方向

- OpenAI 的工程案例把大规则文件改为简短入口、结构化知识与检查机制，并定期修复过时文档。这是从空仓库起步的内部产品实验；作者也承认多年维护效果仍未知。[S04]
- Anthropic 讨论按需检索和跨会话交接：用必要的引用定位资料，持续记录任务进展与验证状态。单靠长上下文和摘要不能保证长任务完成。[S05][S06]
- Mitchell Hashimoto 的个人实践强调根据真实错误改进规则和工具，让 AI 获得快速、有效的反馈。[S07]
- Thoughtworks 的 Birgitta Böckeler 在 2025 年试用规格驱动工具后指出，重复的 Markdown 和过重流程可能增加审查成本；这是有日期与具体环境的实践观察。[S08]
- GitHub Spec Kit 当前的老项目指南建议依据已有项目证据捕获规则，从一个有边界的变更开始，而非先替整个系统补写规格。[S09]

Hacker News 与 Reddit 的一手讨论反映了规则过长、内容显而易见、历史与现状混杂等实际困扰，但也有人报告规则文件对复杂仓库很有帮助。社区经验用于发现问题线索，不等同于受控实验或已验证的行业共识。[S19][S20]

### 2.4 推荐组合与采用顺序

以下是本指南综合证据作出的工程建议，不是已被证明的唯一最优方案。

| 方案 | 在本次工作的角色 |
| --- | --- |
| 精简规则入口、可靠文档、当前状态、验证反馈 | 优先建立的基础 |
| Skills 或重复任务流程 | 在出现稳定、反复执行的程序时采用 |
| 规格驱动开发 | 服务后续有明确边界的复杂变更，避免给所有小任务增加文档负担 |
| 代码地图与语义检索 | 仓库规模或检索困难需要时采用，仍须处理索引新鲜度 |
| 多 Agent | 只有已获授权且任务可独立划分时使用；统一记录结构与整合责任 |
| 全仓一次性重写 | 不作为仓库盘点与知识整理的默认动作 |

代码地图已有实际实现，例如 Aider 按依赖关系与任务相关性选择符号信息。[S13] 对已有业务代码的重构，研究也显示检查与失败反馈有帮助，但受测试覆盖和变更粒度限制，不能保证任意全仓重构正确。[S21]

## 3. 开始前收集哪些信息

### 3.1 尽量自行发现，缺失信息按影响处理

| 信息 | 首选证据 | 缺失时怎么处理 |
| --- | --- | --- |
| 仓库范围与版本 | Git 根目录、提交、工作区状态 | 压缩包可按快照盘点，注明没有历史 |
| 项目技术栈 | 依赖清单、锁文件、构建配置、CI | 不凭文件扩展名推断全部运行方式 |
| 使用的编码工具 | 当前环境、工具版本、用户已说明的配置 | 可以先审计通用内容，具体规则适配列为待核实 |
| 现有约束与规则 | 当前生效指令、仓库规则、组织配置 | 不擅自访问未提供的个人或组织文件；注明可见范围 |
| 当前任务与进度 | 本次指令、现有任务记录、可访问的 issue/PR | 冲突处保留多个来源，不虚构完成状态 |
| 业务目标与兼容要求 | 当前需求、验收标准、决策记录 | 无法推断时集中提问 |
| 测试与运行条件 | 项目脚本、CI、测试配置 | 记录可执行与不可执行检查，不虚报通过 |
| 历史与外部依赖 | Git 历史、子模块、已提供的外部文档 | 缺失不妨碍其他盘点，但限制相关结论 |

无需在开始前要求用户回答一大串可以从仓库找到的问题。只有会改变授权边界、业务结论或关键迁移方式的缺口，才需要用户判断。

### 3.2 基线应记录什么

至少记录：审查日期、仓库标识、提交或快照标识、工作区差异、运行环境、工具版本（可获取时）、检查命令与结果、审查范围。

已有未提交改动时，先记录差异并避免覆盖；在适合当前工作流且已获授权的情况下使用隔离分支或工作区。不要自动 stash、reset 或丢弃修改。没有 Git 历史时，可以用文件清单和内容哈希标识快照。

只读发现命令可以包括以下内容，按所在环境调整；它们不是完整审计流程：

```bash
git rev-parse --show-toplevel
git rev-parse HEAD
git status --short
git ls-files -z
git log -n 20 --oneline
```

git ls-files 主要覆盖已跟踪路径，需结合工作区状态处理未跟踪的项目文件。rg 的默认忽略行为也会影响结果，不能只执行一次 rg --files 就宣布清单完整。子模块、Git LFS 内容、外部工作区和构建产物要分别说明是否实际可用。

## 4. 分阶段执行方法

### 阶段 A：建立基线并识别有效规则

先阅读当前适用的指令，记录规则文件的路径、适用范围、加载方式、相互关系与可见限制。区分根规则、目录规则、个人偏好、组织政策和普通说明文件。

识别项目真正使用的启动、构建、测试和文档检查入口。需要运行命令时先核对命令用途，在已授权环境内执行；仅能静态确认存在的命令，标记为“已找到，未运行”。

**阶段交付：**基线信息、规则来源清单、初始验证结果。不能仅因为某份文件更新时间较新，就认定它比所有其他来源更权威。

### 阶段 B：全仓清点与模块地图

清点至少包括：业务源码、公共库、CLI 与任务脚本、配置、构建与 CI、测试与测试数据、部署与迁移、文档与规则、任务记录、历史归档和生成内容。

文件名与目录名只能提供线索。判断模块职责时，查看入口、导出、调用者和依赖；对关键业务路径追踪实际实现与测试之间的联系。对于多包仓库，要核对跨包调用和共享配置，不能只分别总结各目录。

第三方依赖、缓存、二进制和生成文件通常不需要逐字审查，但应记录分类、来源和排除依据。锁文件、生成器配置和构建入口可能仍是核对版本与行为的重要证据。

**覆盖记录应区分四种深度：**清点、阅读、交叉核对、运行验证。它们不是统一分数；静态文档也可能只有阅读和交叉核对适用。

**阶段交付：**文件清单、模块职责地图、关键依赖关系、审查队列和明确的未覆盖项。审计地图应标注版本；长期架构概览只保留稳定关系，避免另建需要持续手工更新的全符号清单。[S12]

### 阶段 C：文档声明与实际证据核对

针对每份仍有效的规则和项目文档，将可检查的声明拆成具体项目：命令、路径、配置项、接口、数据结构、模块职责、前置条件、完成状态和重要约束。

| 检查对象 | 核对方法 | 常见处理 |
| --- | --- | --- |
| 启动、测试和部署说明 | 对照脚本、CI、配置，并在条件允许时运行 | 修正命令或明确环境前置条件 |
| 模块与接口说明 | 对照实现、调用者、契约及测试 | 更新描述或登记实现偏差 |
| 功能完成记录 | 对照代码、测试、可访问的任务与 PR | 区分已实现、已验证、已发布 |
| 架构约束 | 检查依赖关系和已有决策 | 保留约束，登记违反约束的实现 |
| 旧方案与废弃规则 | 对照替代关系与历史依据 | 标记已被替代并保留来源 |
| 示例、链接与引用 | 检查目标文件、锚点和示例所需版本 | 修复失效项或标为待核实 |

“代码中存在功能”不等于“功能可用”，更不等于“已部署给用户”。只有看到相应证据，才能写对应状态。测试通过支持所覆盖的行为，不是全部业务行为的正确性证明。

出现冲突时记录双方原文位置、支持依据、影响和建议。不以“代码为唯一真相”“最新时间戳优先”或“多数文件都这样写”为通用裁决规则。普通资料中的指令性措辞也不自动成为有效项目指令。

**阶段交付：**发现台账，以及每一项“保留、修正、合并、迁移、归档、待确认”的具体判断。

### 阶段 D：整理规则与文档

先处理证据明确的问题：失效路径、错误命令、已确认的过期描述、重复内容和入口遗漏。对于语义性改动，说明旧要求、新表达以及为什么仍保留原意。

根规则重点保留：每次都需要的少量约束、项目特有的操作方式、难从代码推断的陷阱，以及相关资料入口。模块专用规则放在该工具支持的局部机制中；复杂操作流程采用按需读取的文档或已有 Skill。

每条规则可用以下问题筛选：

- 它现在仍然正确吗？证据或理由是什么？
- 它适用于全部任务，还是只适用于某模块或操作？
- AI 能否从现有脚本、配置或代码轻易得到同样信息？
- 是否与另一条要求冲突或重复？
- 是否需要程序化检查，而不仅是一句自然语言要求？
- 如果移出常驻入口，AI 能否在需要时找到它？

没有通用的“科学最佳行数”。可以设项目自己的入口预算作为维护提醒，但不能为了达标删除重要约束，也不能用大量自动导入把实际加载量藏起来。

**阶段交付：**实际修订的文件、规则处置表、迁移映射和仍需决定的语义冲突。

### 阶段 E：处理越来越长的进度记录

按内容用途迁移，不按文章篇幅机械切割：

1. 提取所有未解决事项，包括复选框、TODO、临时绕过、阻塞、待验证声明，以及“以后处理”等自然语言表达。
2. 为事项建立稳定标识或关联现有任务编号，核对当前状态并记录证据。
3. 将当前目标、阻塞、下一步和必要验证放入简短状态入口，采用更新现状的方式维护。
4. 复杂任务保留自己的计划与交接记录；重复的汇报文本可归档。
5. 长期有效的决策及理由转入对应决策记录。没有证据的历史意图标为未知，不能补写成已确认事实。
6. 归档旧记录，标明时间范围、原位置和替代入口；如添加归档说明，应注明这是本次整理追加的元信息。
7. 对迁移前后未解决事项逐项对账，确认它们都有明确去向或关闭依据；检查新旧链接。

历史中被替代的决定仍有追溯价值。ADR 的原始做法是保留旧决定并注明被替代，而非擦除历史。[S11]

**阶段交付：**当前状态入口、归档内容、迁移关系，以及没有遗失未完成事项的核对记录。

### 阶段 F：验证、复核与交接

按实际修改范围验证，不为轻微文档修订自动增加全仓昂贵测试。至少检查差异是否符合任务范围、文档与规则是否保持原意、内部路径与引用是否有效，以及规则实际加载情况。

对文档中的关键操作命令，优先验证启动和测试等后续开发必需的入口。不能运行时记录原因、已检查的静态证据和需要怎样补验。

使用新会话验证交接效果：让 AI 找出当前目标、相关实现入口、适用规则和验证方式。通过工具提供的加载记录、引用或诊断信息确认生效来源；AI 自述“我读到了”只能作为辅助。

最终按“已证实、已修改、已验证、仍待确认”汇报。用范围与证据描述完成程度，不用文档数量或删除行数证明质量。

### 大仓库与多会话补充

按模块或业务域建立审查队列，每次结束记录：当前基线、已覆盖区域、重要发现、已修改文件、未验证项和下一步。下一会话首先核对这些记录与当前差异是否仍相符。

如果仓库在审查期间有新变更，将其纳入增量复核；不要继续把旧版本的结论标为当前结论。全部模块阶段完成后，再专门检查跨模块接口与依赖，避免每个局部看似正确而整体关系遗漏。

若使用多 Agent，应先明确授权与每个代理的范围；统一证据字段，由一个负责人整合跨模块结论并处理冲突。代理之间一致同意也不替代源码与运行证据。

## 5. 整理后应形成怎样的知识结构

### 5.1 最小结构与单一维护位置

以下路径只是示例。已有等价文件或任务系统时优先复用，不需要按表创建空目录。

| 载体示例 | 记录内容 | 更新条件 |
| --- | --- | --- |
| AGENTS.md 或工具对应入口 | 稳定约束、特殊命令、阅读导航 | 约束变化或确认新的高价值经验 |
| README.md | 项目用途、基本使用与入门 | 使用方式或项目定位变化 |
| ARCHITECTURE.md | 稳定模块关系、职责与边界 | 架构出现实质变化 |
| docs/current-state.md 或现有看板 | 当前目标、阻塞、下一步 | 状态变化 |
| docs/plans/ 中的任务记录 | 某项复杂工作计划和验证 | 任务推进，完成后归档 |
| docs/decisions/ | 重要选择的背景、理由和代价 | 重要决策新增或被替代 |
| docs/archive/、Git、PR | 历史过程及其来源 | 按需归档和追溯 |

一条事实尽量只有一个主要维护位置，其他位置通过短说明和引用使用它。若现有看板已经权威记录任务状态，不要再强制维护一套完整 Markdown 待办表。

### 5.2 每类信息应该怎样保持可信

当前说明应标明适用版本或核验范围；生成的参考资料应注明生成来源；临时诊断报告应说明它是某次快照；历史文档应可识别为历史。

“最后修改日期”只能说明有人改过文件，不能代替“内容已按某个版本核对”。也不要每次任务给所有文档刷新核验日期。

自动记忆可辅助延续个人偏好和经验，但重要项目事实应有团队和后续环境可访问的来源。工具自身记忆的共享、同步和加载范围要实际确认，不能假设换一台机器仍会自动继承。[S15]

### 5.3 规则变化与任务变化分开处理

每次任务检查相关知识是否变化，但没有变化就不改。新增一个局部功能通常无需修改根规则；改变构建方式、接口兼容要求或模块边界则应同步对应内容。

对于有确定判定方式的重复问题，优先复用现有 lint、类型检查、链接检查、契约测试或架构约束。新增脚本和 CI 配置属于单独的工具改动，按用户已授权范围执行；不能把增加基础设施隐含进纯文档整理任务。

## 6. 不同工具的规则加载不能混用

本节用于提示核对方向，不是固定不变的产品规格。执行时以实际工具、版本、工作目录、产品界面和最新官方说明为准。

| 工具 | 本次核验到的机制 | 执行时应检查 |
| --- | --- | --- |
| Codex | 官方说明区分全局与项目指令，按目录链构建上下文，并有覆盖文件、候选文件名和大小限制 [S14] | 从哪个目录启动、实际读取哪些文件、是否被覆盖或截断；不能假设全仓所有子目录规则自动常驻 |
| Claude Code | 支持 CLAUDE.md、路径作用域规则及自动记忆；导入文件仍占启动上下文 [S15] | 区分常驻导入与按路径读取；检查实际记忆范围，避免将文件拆分误当成减少加载 |
| Cursor | 支持项目规则和适用方式，官方建议按主题拆分，并从真实重复错误中增加规则 [S16] | 是否始终应用、按模式匹配或需手动调用；确认实际生效情况 |
| GitHub Copilot | 支持情况因 Chat、CLI、云代理、代码审查及 IDE 而异 [S17] | 不把某个界面的行为推广到其他界面 |
| Copilot CLI | 当前文档说明会组合多份适用指令，但未定义这些文件之间的一般优先级；某些文件中的 @ 引用会立即展开 [S18] | 主动消除冲突，不能套用“最近文件必定覆盖全部其他文件”的通用规则 |

本次查阅的 Codex 文档列出默认 32 KiB 合并指令限制；Claude Code 文档区分 CLAUDE.md 的简洁性建议与自动记忆索引的前 200 行或 25KB 加载限制。它们是不同机制，不是通用的“AI 最佳记忆长度”。细节可能随版本变化。[S14][S15]

如果多个工具共用一套长期约束，可以采用一个主要来源和各工具的轻量入口，但必须验证该工具是否支持引用及其加载语义。不要只创建指向其他文件的链接，就假定规则内容已经加载。

## 7. 交付物与记录模板

### 7.1 文件规模按实际需要决定

小仓库可将下面的记录合并在一份审计报告中。文件较多时，覆盖表使用 CSV 便于筛选，其余继续使用 Markdown。不要把同一条发现分别完整复制到多个报告里，使用稳定编号关联即可。

建议记录字段较多，实际可以删去没有用途的字段，但不能删去来源、状态、影响和验证结果这些核心信息。所有模板示例都需用实际检查结果填写。

### 7.2 覆盖记录

每个纳入范围的项目文件至少有一条记录。大量同类第三方或生成文件可以按明确模式聚合，但需保留可恢复的成员清单或清单来源；不能让关键自有代码隐藏在聚合项中。

```text
path_or_pattern: 实际相对路径或明确集合
category: 源码 / 配置 / 测试 / 文档 / 规则 / 生成物 / 其他
module: 所属模块
baseline: 提交、快照或哈希
inventory_status: 已清点 / 待清点
content_review: 已读 / 部分阅读 / 未读 / 不适用
cross_check: 已核对 / 未核对 / 不适用
runtime_check: 通过 / 失败 / 未运行 / 不适用
evidence: 相关路径、符号、命令结果或发现编号
exclusion_or_gap: 排除理由、无法读取原因或剩余工作
```

### 7.3 单条发现记录

```text
id: F-001
category: 文档漂移 / 规则冲突 / 状态错误 / 重复 / 其他
statement: 发现了什么
evidence: 来源路径与小节、符号或版本固定的行号
evidence_status: 已证实 / 推断 / 待确认
impact: 会怎样影响后续开发
priority: 阻塞当前工作 / 应近期修复 / 可后续处理
proposed_action: 保留 / 修正 / 合并 / 迁移 / 归档 / 待确认
resolution: 实际处理方式或尚未执行的原因
validation: 检查方法与结果
```

行号会随编辑变化，重要证据最好同时保留提交标识或小节、符号名。置信状态和处理优先级是两个维度：影响大的怀疑仍然是怀疑。

### 7.4 文档与规则处置表

| 原位置与内容 | 处置 | 目标位置 | 依据 | 验证 |
| --- | --- | --- | --- | --- |
| 填写真实路径及小节 | 保留、修正、合并或归档 | 填写实际路径 | 来源或发现编号 | 内容与链接检查结果 |

规则合并时，额外检查：作用域是否扩大或缩小，例外是否遗失，强制要求是否变成建议，旧引用是否仍有效，以及历史约束是否被误认作当前约束。

### 7.5 当前状态记录

```text
核验基线：
当前目标：
已实现且已验证的相关能力：
未完成事项及其标识：
阻塞与待用户判断事项：
下一步可执行动作：
相关实现、规则与任务文档入口：
最后执行的关键检查及结果：
尚未验证的范围：
```

这里保留与继续工作相关的状态，不复制完整提交历史。对于“已完成”事项，应能跳转到相应验证依据；无证据时使用“待验证”或更精确的状态。

### 7.6 验证记录

```text
check_id:
purpose: 本次检查要证明什么
command_or_method:
working_directory:
environment_and_baseline:
result: 通过 / 失败 / 阻塞 / 未执行 / 不适用
observed_output: 简要结果或日志位置
limitations: 不能由本次检查证明的内容
related_changes:
```

### 7.7 最终交接报告

报告应依次说明：范围与基线、主要发现、实际修改、验证结果、尚未完成或待确认事项、下一步。附上文件入口和迁移关系。

对于涉及业务意图的待确认项，给出具体问题和已有证据，例如“文档要求保留旧 API，但实现已移除兼容入口；是否仍需要支持旧客户端？”不要只写“请人工复核”。

## 8. 验收与长期维护

### 8.1 本次整理的验收清单

- [ ] 报告清楚标明审查版本、工作区差异和访问范围。
- [ ] 纳入范围的模块、文档、规则均进入清单；未读、未核对和排除项可见。
- [ ] 重要结论有来源；事实、推断和待确认意图区分明确。
- [ ] 已检查关键模块之间的依赖，而非只有逐目录总结。
- [ ] 规则修订保留有效约束的含义、作用域和例外。
- [ ] 过期、重复、冲突的内容均有明确处置或未解决理由。
- [ ] 历史归档可追溯，未完成事项迁移前后逐项对账。
- [ ] 内部链接和关键命令已按条件验证，不能运行的部分已标注。
- [ ] 新会话能找到当前状态、对应实现和有效规则；加载验证依据已记录。
- [ ] 差异属于已授权范围，用户原有改动没有被覆盖。
- [ ] 报告使用实际结果，没有空模板冒充完成的检查。

“清点覆盖率”可以统计，但“100% 文件被列出”不等于“100% 内容被理解”。不要给不同审查深度合成一个看似精确的总质量分。

### 8.2 证明它改善了后续 AI 工作

如需比较整理前后的效果，可从仓库挑选几个有代表性的任务，例如定位一个业务入口、找出正确测试方法、解释一个架构约束、确定当前未完成事项。

固定任务输入、代码基线、模型与配置；分别使用整理前后的规则和文档，用新会话运行。执行型任务使用隔离副本，避免前一轮修改泄漏答案；重复运行时避免把已知解决方案写进另一组上下文。

观察任务正确性、违反约束次数、人工纠正次数、定位耗时与资源消耗。少量重复可用于发现实际改进，但样本很小时只能称为项目内试评，不能宣称统计证明或普遍优势。

本次用户只要求盘点与知识整理时，不必额外实施业务功能来完成评测。优先用定位、解释、计划和指令加载验证；更完整的开发任务评测可以随下一次真实任务进行。

### 8.3 每次任务的更新触发

| 发生的变化 | 应检查或更新 |
| --- | --- |
| 启动、构建、测试、部署入口变化 | 脚本说明、相关文档与规则命令 |
| 模块职责或公共契约变化 | 架构概览、接口说明，必要时补决策记录 |
| 任务推进、验证完成或出现阻塞 | 当前任务状态 |
| 任务完成 | 验证依据、剩余事项与计划归档 |
| AI 重复犯同类错误 | 原因分析，选择补规则、改工具或增加检查 |
| 只有局部实现细节变化 | 相关代码与就近说明；通常无需改根规则 |

维护频率按变更量和实际问题设定，不套用固定“每周重写全部规则”。自动化维护也需要范围与授权：可以先报告疑似漂移，或在允许时生成可审查的修订；不要把过期检测直接等同于自动删除。

## 9. 常见失败方式与纠正办法

| 失败方式 | 为什么会出问题 | 纠正办法 |
| --- | --- | --- |
| 要求“彻底优化”，不定义范围 | AI 可能扩展成任意代码改造 | 明确本次以盘点、文档和规则为范围 |
| 只看目录树就写完整架构 | 名字不能证明实际职责 | 追踪入口、调用与配置并记录证据 |
| 全量复制旧规则再润色 | 重复与过期信息继续存在 | 逐条核对并决定保留、迁移或处理 |
| 强制每次更新根规则 | 规则被任务流水账淹没 | 检查是否变化，按内容类型更新 |
| 拆分文件后仍全部自动导入 | 实际常驻上下文没有减少 | 核对工具加载语义并验证 |
| 将当前实现自动当成正确需求 | 可能把缺陷写成正式规格 | 区分实际行为与业务意图 |
| 用“摘要完成”替代迁移核对 | 未完成事项和决策理由容易丢失 | 按稳定标识逐项对账并保留历史 |
| 根据静态工具输出直接删文件 | 入口与动态引用可能没被识别 | 核查分析配置、动态入口及外部调用 |
| 为所有小改动增添完整规格流程 | 文档数量和审查成本继续上涨 | 流程复杂度与任务复杂度匹配 |
| 让 AI 用自己的结论证明自己正确 | 相同误判可能被重复确认 | 用源码、独立检查、基线和实际反馈复核 |

以 JS/TS 的 Knip 为例，官方列出了动态导入、生成文件、插件缺失、跨工作区路径等影响未使用文件分析的情况。工具报告需要结合项目入口与配置理解，而不是直接当删除清单。[S22]

本指南推荐的最终状态是：后续 AI 能准确找到当前事实、理解重要约束、继续未完成工作，并通过检查发现自己的错误。规则文件更短、文档更多或目录更整齐，都不能单独作为成功依据。
